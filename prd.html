追竞｜电竞赛事提醒小程序 PRD

版本：V0.1 · 需求与交互验证版
更新：2026-10-28
目标平台：微信小程序；本轮交付为浏览器交互 Demo，不是已发布的微信小程序。

每一场热爱，都准时在场。关注喜欢的游戏、赛事、战队和选手，在比赛当天或开赛前收到提醒。

1. 已确认的需求与本轮边界

用户已确认：采用微信小程序；产品范围包含端游与手游电竞；当前没有小程序账号及数据源，先交付 PRD 和任何人都能访问的 Demo 链接。

“喜欢的战斗”按上下文解释为“喜欢的战队”。产品定位为观赛工具，不涉及参赛组队、游戏对局提醒或投注。

本轮要验证：用户能否找到比赛、建立关注、理解提醒授权、预约合适时间，并在提醒中心修改或取消。无需手机号、账号注册或付费即可体验。

本轮不接真实赛程、不请求微信授权、不发送通知、不开发正式后台。界面、字段、时间规则和任务链路用于确认产品方案。

2. 目标用户与问题

用户 典型情境 需要解决的问题
战队粉丝 支持的战队参加多个赛事 不必逐个赛事查赛程
选手粉丝 选手转会、替补或临时换队 按实际参赛关系找到相关比赛
多项目观众 同时看端游和手游赛事 统一时间与入口，避免遗漏和撞期
轻度观众 只想看决赛或某一场 无须关注整个赛季，直接预约单场

核心价值：减少找赛程和记时间的成本。首页优先展示近期赛程与关注理由，不以资讯流、比分榜或社区内容稀释主任务。

4. “全电竞”的覆盖策略

全电竞是产品的长期覆盖目标，不能理解为首日已拥有所有比赛。游戏目录与赛程接入状态必须分开记录和展示。

4.1 项目分类

一级：端游电竞、手游电竞。二级：具体游戏。游戏内依次组织赛事品牌、赛季／届次、阶段和比赛；跨端项目按实际比赛平台标注，可多端归类。

Demo 的 12 个展示项目：英雄联盟、无畏契约、反恐精英 2、Dota 2、穿越火线、守望先锋，以及王者荣耀、和平精英、英雄联盟手游、使命召唤手游、决胜巅峰、荒野乱斗。该列表为体验样本，不是穷举，更不表示已取得这些项目的数据授权。

4.2 覆盖台账

每个项目／赛事维护：数据提供方、授权范围、地区、赛事级别、时间精度、更新方式、最后成功同步时间、战队与选手支持程度、负责人。

对用户显示四种状态：已接入、部分覆盖、待接入、同步异常。未接入时显示“暂无已接入赛程”，不能误称“没有比赛”。不能静默用 Demo 数据补齐真实模式。

4.3 接入阶段

  1. 数据验证：分别选择至少一个端游和一个手游赛事，取得可靠、允许使用的数据源，验证时间和参赛关系。
  2. MVP：上线通过验证的赛事范围，明确显示覆盖边界；不能以“大部分游戏”替代实际验收。
  3. 扩展：按用户关注需求接入剩余头部项目和区域赛事，再逐步扩展长尾。每个项目单独验收后标为已接入。

优先选择官方／授权赛事数据；第三方聚合 API 可作为候选，须核实其实际游戏和联赛覆盖、使用权与更新能力。PandaScore 的官方文档展示了赛事层级与即将开赛接口，但不能据此推断它能覆盖全部端手游电竞。没有接口的赛事可用经核实的运营录入，必须记录来源与最后核验时间，不依赖未经评估的网页抓取。

比赛结构必须支持两队对抗、多队同场和个人参赛。和平精英等多队积分项目不应在正式产品中强行转换成两队对战；Demo 为简化视觉展示使用了明确标注的示例对阵，正式开发必须替换。

5. 信息架构与主流程

5.1 三个主页面

  • 赛程：近期比赛、日期、游戏／平台筛选、搜索、只看关注、比赛详情、预约入口。
  • 我的关注：游戏／赛事／战队／选手分类、搜索、关注或取消关注、已关注筛选。
  • 提醒中心：按提醒时间排序的待提醒记录、修改／取消、消息状态及失败处置。

移动端使用底部三项导航，桌面浏览 Demo 使用侧边导航。产品文档入口与 Demo 标识保持可见。

5.2 关注后发现比赛

进入“我的关注” → 选择类别 → 搜索并关注 → 回到赛程打开“只看关注” → 查看命中比赛及关注理由 → 为感兴趣的单场预约。

同时关注赛事、战队、选手时，任一匹配即展示；同一场只展示一次，可合并多个关注理由。关注选手表示“可能相关”，实际参赛须由赛事报名或阵容数据确认。

5.3 单场预约

查看比赛 → 点击“提醒我” → 选择提醒时间 → 用户主动点击授权 → 微信返回同意 → 服务端成功持久化 → 显示“已预约”。任一步失败都不能显示已预约。

微信拒绝时保持比赛详情，提供返回赛程或重新操作入口，不反复弹出授权。不以打开页面、关注成功或勾选设置替代微信授权。

5.4 接收提醒

任务到期 → 校验最新赛程与预约状态 → 幂等领取任务 → 发送微信订阅消息 → 记录结果。通知展示赛事、对阵／参赛者、开赛时间，并跳转对应比赛详情。

“接口发送成功”不等于“用户已看到”。如无平台阅读回执，不展示已读状态，也不把发送成功率称为送达率。

6. 详细业务规则

6.1 时间与展示

存储使用 UTC 时间戳，保留源时区；MVP 用户展示统一为北京时间（UTC+8），不依赖手机所在时区。日期筛选也以 UTC+8 的自然日计算。

选项 计算规则 示例：10 月 28 日 19:00 开赛
比赛当天 比赛所在自然日 09:00 10 月 28 日 09:00
赛前 3 小时 开赛时间减 180 分钟 10 月 28 日 16:00
赛前 1 小时 开赛时间减 60 分钟 10 月 28 日 18:00
赛前 15 分钟 开赛时间减 15 分钟 10 月 28 日 18:45
比赛开始时 计划开赛时间 10 月 28 日 19:00

预约必须满足提醒时间晚于当前服务端时间，且不晚于开赛时间；已过时间禁用并说明原因。凌晨比赛的“当天 09:00”晚于开赛，应禁用，不自动改为前一天。赛前提醒跨日时显示完整日期。

默认建议赛前 1 小时。如果该时间已过，正式版选择最接近且仍有效的选项；如果所有选项都不可用，不允许预约。

“比赛开始时”指按最新计划时间触发，不承诺基于直播开播或比赛真正开局。若未来接入可信实时开赛信号，应另行定义提醒模式。

6.2 单场预约与授权

MVP 每位用户每场最多一个有效提醒时间，避免一次授权对应多次发送的误解。赛前多档同时提醒不在本次范围；未来需要按真实授权次数与模板条件设计。

同场再次预约更新原任务，不新增重复记录。修改未发送预约时仍只有一次计划发送；若需要新的平台授权，应由用户主动触发。取消本地预约不会伪称撤销了微信账号对模板的授权。

取消关注不自动取消已经主动预约的单场消息，并在交互中明确提示；用户到提醒中心单独取消。重复取消应返回一致结果。

一次性订阅不能被宣传成“关注一次、永久推送所有未来比赛”。长期订阅能否使用必须以该小程序真实服务类目与可选模板为准；没有条件时采用逐场主动订阅，不承诺绕过规则。

6.3 赛程变化

  • 改期：保留比赛稳定 ID，增加 scheduleVersion；重算未发送任务，旧版本禁止发送；详情标记原时间与新时间。
  • 提前：若重算提醒时间已过但比赛未开始，可在授权仍有效时发送一次“即将开始”提醒；比赛已开始则标记错过，不补发误导性的赛前消息。
  • 延后：改为新时间触发；已发送的提醒不得默认再次发送，额外消息取决于另一次合法授权。
  • 时间待定／取消：停止旧提醒任务，前台显示原因；没有合法消息额度时不保证额外推送改期或取消通知。
  • 来源冲突：标记待核验，不把两个来源作为两场比赛；展示最后确认时间，不按未经确认的新时间发送。

6.4 选手与阵容

实体以稳定 ID 区分，同名选手通过项目、队伍和地区辅助识别。别名用于搜索，不能作为唯一 ID。

选手与战队关系须有有效时间区间，按比赛发生时间匹配。官方公布首发时优先使用首发；未公布则显示“所属战队参赛，出场待定”。转会后不把旧战队未来比赛持续算给该选手；替补关系不可直接宣称确定登场。

7. 数据与技术方案（正式开发建议）

建议先采用微信原生小程序＋云开发数据库／云函数＋定时任务；最终选型须在账号、服务类目、消息模板和数据来源明确后确认。本次不以 Demo 的静态代码代替生产方案。

实体 最小关键字段
Game id、name、platforms、aliases、coverageStatus
Competition / Edition id、gameId、name、season、region
Team / Player id、name、aliases、gameId
RosterMembership playerId、teamId、validFrom、validTo、role、source
Match id、editionId、stage、format、participants[]、scheduledAt、status、scheduleVersion、source、sourceUpdatedAt
Follow userId、targetType、targetId、createdAt
Reminder userId、matchId、rule、triggerAt、scheduleVersion、status、templateId
SendAttempt reminderId、attemptId、platformResult、requestedAt、finishedAt

用户身份从微信服务端可信上下文取得，不接受客户端传入任意 OpenID。客户端不得写入正式赛程、消息发送状态或他人预约。API 密钥、AppSecret 及服务端令牌不得出现在小程序包或公开 Demo 中。

业务接口：查询赛程、查询实体、增删关注、创建／更新预约、取消预约、查询本人预约。后台同步与消息发送接口只允许受控服务调用，客户端不直接执行。

7.1 提醒任务状态

状态：待提醒 → 发送中 → 已发送／失败／结果待核实；另有已取消、比赛取消、已过期。

使用数据库事务或条件更新领取任务；以用户＋比赛＋预约版本作为幂等约束。发送前再次检查是否取消、是否改期、是否过期。收到明确可重试错误后按有界退避重试；额度不足、授权拒绝和字段不合法不盲目重试。

微信接口超时但结果未知时，可能已消耗额度；进入“结果待核实”，不能简单回到待发送无限重试。监控应覆盖重复任务、任务积压、消息失败与数据同步滞后。

定时扫描频率建议为每分钟，属于待验证设计。根据云服务实际配额、流量与执行时长评估拆分批次；不承诺现阶段已经具有大规模推送能力。

8. 异常、空态与隐私

情况 用户反馈 处理
没有关注 引导关注战队或选手 保留浏览全部比赛入口
筛选无结果 当前条件暂无匹配 支持清除筛选
数据源未接入 尚未接入该赛事 不显示虚构数据冒充真实数据
网络失败 加载失败，请重试 保留已加载数据及更新时间
授权拒绝 未开启本次提醒 不创建有效发送任务
预约保存失败 预约未保存 保留选择，允许显式重试
微信发送失败 显示可理解的原因 无有效授权则引导重新预约
比赛取消／待定 显示状态及更新时间 停止旧发送任务

正式版最小化保存用户标识、关注与提醒记录，不默认索取手机号、通讯录或精确位置。提供取消关注、取消提醒、清除个人数据的入口；保存期限、隐私说明、上线服务类目需在上线前确定并评审。

Demo 不向业务服务器上传关注与预约；只使用当前浏览器 localStorage，访客之间不共享。清除浏览器数据会丢失体验记录；同一浏览器可通过“重置体验数据”清除。公开托管服务自身可能记录常规访问日志，不能把产品不采集信息表述为整个网络链路绝无日志。

9. 体验与视觉规范

风格：深色观赛日历，荧光绿强调预约和选中状态，项目色辅助区分游戏。信息优先顺序为开赛时间、对阵、赛事、预约状态；不依赖颜色独自传递状态。

手机端优先，兼容 360–430px 常见宽度，页面无横向溢出。主操作触达区域至少 44px，弹窗可关闭并支持键盘焦点；减少动态效果设置生效。正式微信版使用平台授权弹窗，不能画一个假微信系统授权窗口替代。

Demo 所有阵容和赛程为虚构。固定演示时钟为 2026-10-27 12:00（UTC+8），不会随着现实时间过期，也不会自动倒计时推送。首屏示例与真实上线模式严格区分。

10. 验收标准

10.1 本次 Demo

  1. 公共 HTTPS 链接可打开，首次体验不要求业务登录；手机与桌面均可使用。
  2. 三个主页面可切换，端游／手游和日期筛选生效，支持名称搜索。
  3. 关注任一类型后，“只看关注”能列出匹配赛程；多重匹配不会重复展示。
  4. 单场详情可关注战队、赛事与选手，已有关注状态一致。
  5. 预约成功出现在提醒中心；再次设置更新同场记录，取消后从中心移除。
  6. 当天已过的提醒时间不可选择；跨日规则使用 UTC+8，不受设备时区影响。
  7. 刷新后浏览器本地数据保留；重置只清理本 Demo 的数据。
  8. 通知预览明确标注模拟，不弹系统通知、不发送微信消息。
  9. PRD 可以在线阅读和下载；公开页面不含真实用户数据或密钥。

10.2 正式 MVP 上线门槛（本次未执行）

  1. 使用真实小程序账号，在真机完成授权同意／拒绝／保存失败／发送失败链路。
  2. 对通过验收的赛事逐一核对时间、来源、阵容和多队赛事结构。
  3. 定时任务重复运行或并发运行不会创建重复发送；改期与取消可阻止旧版本消息。
  4. 验证跨日、凌晨、时区、延期、提前、取消、转会、替补和时间待定。
  5. 权限校验阻止查询或修改其他用户记录；客户端无法读取数据源密钥。
  6. 确认真实模板字段、跳转路径、运行配额与服务类目可用；满足实际发布审核要求。

11. 衡量指标与阶段交付

指标为待上线验证的设计，不是当前已采集数据。

  • 激活：首次访问用户中完成至少一次关注的比例。
  • 预约转化：查看比赛详情后成功创建提醒的用户比例，区分授权拒绝和保存失败。
  • 发送成功率：微信返回成功的发送请求数／有合法授权且到期的有效提醒数。
  • 时间准确性：任务计划时间与实际发送请求时间的差值；初始目标 P95 不超过 2 分钟，须压测与真机验证。
  • 赛程可信度：已核验比赛数、改期更新耗时、错误时间反馈率；按来源分组。
  • 留存：完成关注／预约用户的下一比赛日回访情况；不以通知预览点击代替真实通知打开。

交付阶段：A 需求与交互验证（本轮）→ B 账号／模板／数据源可行性验证 → C 小程序与服务端闭环 → D 有限赛事灰度 → E 扩大端游手游覆盖。未明确数据源与类目之前，不估算“全电竞上线”的确定日期。
